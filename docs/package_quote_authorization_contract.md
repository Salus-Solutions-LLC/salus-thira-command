# Package quote and authorization contract

**Status:** implementation contract for review, 29 September 2026. **Authority:** Salus Program Charter SAL-D080–SAL-D090. **Handling:** Salus Internal Confidential. This document does not authorize a price, engagement, report issue, or production deployment.

## Why this workflow is needed

The Protection Advisor can suggest a Level 1 band and give a draft scope receipt. The current SalCAPA assessment record stores a **requested** level, band, Access/Standard option and covered operation. These fields do not prove eligibility, establish a fixed quote, authorize work, qualify a predecessor or release any of the four reports. The next implementation must make those distinctions visible and enforce them in the API, not only in the page copy.

In the production-locked candidate, a signed-in Member account receives only an `Awaiting Salus signer review` state until Salus records a valid exact-quote signer review. It receives no quote terms, fee, agreement reference or download link before that review. After review, only the reviewed Client Executive may see the terms; a changed review digest fails closed. The dashboard explains the pending state without presenting it as a historical quote or an offer. These source controls require authenticated browser and tenant proof before release.

## One package identity and states

One governed package identity binds the Protected Member and tenant, decision owner, covered and excluded units, level, band, Access/Standard option, source Protection Advisor submission and receipt version, written scope version, quote version, agreement version, four report IDs and the predecessor package. Preserve immutable prior versions; a changed scope gets a new version of the **same** package, not another Member submission or duplicate report.

| State | Meaning | Permitted next action |
|---|---|---|
| Requested | Member or Salus named a possible path | Scope review; no paid work |
| Scoped | Salus named boundaries, exclusions, required evidence, deliverables and estimated effort | Eligibility and capacity review |
| Quoted | Authorized Salus commercial reviewer approved one fixed fee, assumptions, taxes if applicable, separate-service exclusions and validity period | Member accepts or requests change |
| Authorized | Authorized Member decision owner accepted the exact quote, terms, handling, transfer method and schedule; Salus accepted capacity | Secure intake and assessment work |
| In progress | Work is underway within the authorized boundary | Analyst and evidence review |
| Ready for release | Four exact report versions passed source, method, privacy, style, accessibility and qualified review gates | Human issue decision |
| Issued | Four separately identified reports and SalCAPA summary were released to the approved recipients | Decision tracking and reassessment |
| Superseded or declined | Prior quote/scope replaced or Member declined | Preserve audit record; no silent restart |

## Transition rules

1. Level 1 is the first paid package. Level 2 authorization requires a qualified issued Level 1 predecessor covering the same decision unit or an explicitly reviewed changed boundary. Level 3 requires qualified issued Level 2. A report filename, title, score, or requested state is not predecessor proof.
2. Band A means one combined decision unit. Band B requires distinct findings and a comparison for two named units or operations. Band C requires group-level priorities. Address count, revenue and headcount are scoping clues, not automatic band decisions.
3. Level 1A Access uses $1,500 only after Salus checks the simple eligible boundary and capacity. Level 1A Standard and every other level/band have no public fixed price until approved. The quote stores the exact amount, currency, scope assumptions, dates, owner and expiry. Separate SalOPS services receive separate scope and authorization.
4. Any change to covered units, report deliverables, price, dates or Member handling after quote must produce a new quote version and a fresh acceptance. The old authorization cannot silently cover new work.
5. Secure transfer starts after authorization. Request a short first packet and record missing material as missing; do not require personal directories or sensitive individual records by default.
6. Report generation may remain draft during work, but issue and distribution require exact-version human approval. The SalCAPA summary links the four approved report IDs and tells the Member which options are included recommendations and which are separately proposed services.

### Four-product report and predecessor proof

The current `report_versions` table holds an Executive snapshot of an assessment. Its `Released` state does **not** prove a SalINTEL™, SalTHIRA™, SalOPS™ or SalCAPA™ package report was issued, and must never qualify Level 2 or Level 3 entry. Add a separate governed package/report lineage record before removing the Level 2/3 quote block. Preserve any historical Executive snapshot as its own identity; do not relabel it or create duplicate Member reports.

For each of the four products, the lineage record must bind one package and tenant, its exact level/band/variant and covered/excluded decision boundary, assessment/scope version, product report ID and immutable version, approved method and template version, original document location and SHA-256, status, qualified reviewer, approving and issuing authority, recipient/issue timestamp and supersession link. The SalCAPA™ record additionally names the exact issued SalINTEL™, SalTHIRA™ and SalOPS™ versions it summarizes and records any returned conflict. Use new report versions under the same product identity when a change requires revision.

A predecessor qualification decision may be recorded only after the four distinct products have passed their own review and release gates, the SalCAPA™ report reconciles the other three, the signed prior package boundary and authorization match the issued scope, and the qualified reviewer has assessed unresolved limitations and any changed boundary for the next level. Store the prior package ID, four report IDs/versions/hashes, decision unit and exclusions, qualification basis, reviewer, decision date and immutable digest. A merely requested level, accepted quote, Executive snapshot, draft report, filename or database status without exact document/recipient proof is insufficient. Revalidate the predecessor at the next quote and again at Member acceptance; a changed or withdrawn issue must fail closed until a new qualified decision is recorded.

## Required implementation evidence

- Tenant-scoped tables or governed records for scope versions, commercial approval, Member acceptance, predecessor qualification, four-report links, and status events. Include actor, role, timestamp, source/decision basis and content hash. Use idempotency keys for accept/retry operations.
- API guards for every transition, including role and tenant checks, stale-version rejection, contradictory scope rejection, conditional Access eligibility, predecessor validation and separate SalOPS authorization.
- Plain-language views that show **possible path**, **fixed quote**, **authorized package**, **work status** and **issued reports** as different states. Show the exact covered unit, exclusions, fee, dates, Member action and what Salus will provide.
- Tests for A/B/C boundaries, declined or expired quotes, changed scope, repeated acceptance, cross-tenant access, missing predecessor, older issued versions, missing source receipt, and four-report release blocking. Verify existing governed submissions and reports are not duplicated by migration or retry.
- Reviewed database migration, backup and rollback; protected storage and retention review; native Word/PDF/print parity; accessibility; Azure and Wix end-to-end checks under governed release. Record actual image version and observed deployment before claiming live acceptance.

## Candidate implementation and remaining gates

The draft branch now has tenant-scoped, versioned Level 1 package quotes and exact-version Member acceptance records bound to the existing assessment. A Salus director or administrator records the written boundary, exclusions, fee, dates, agreement reference/hash, capacity and Access eligibility basis. Eligible Level 1A Access is constrained to $1,500; other package fees still require commercial approval. A signed-in Client Executive accepts the exact quote and agreement hashes using an idempotency key. The API rejects altered, expired or superseded quotes, cross-tenant reads and requoting after acceptance. Portable backup includes both records. The write endpoints are **disabled by default** and **always blocked in production** until the agreement delivery, authority and release gates below are implemented and reviewed. Local tests exercise only the enabled nonproduction candidate.

The nonproduction Member dashboard now shows a read-only summary of the selected assessment's latest governed quote: current status, level and band, exact fee, covered work, exclusions, included reports, Member inputs, evidence and clarification allowances, dates, change triggers and a link to download the exact agreement. Dates display day-month-year. The screen has no purchase control; an expired or changed-scope quote retains its status warning. This candidate view needs authenticated browser, accessibility and nonexpert comprehension review before release.

The candidate now stores the exact agreement PDF in tenant/assessment-scoped storage after a Clean malware scan, binds its artifact ID and SHA-256 to the quote, verifies the bytes on download, and records which signed-in Client Executive downloaded that exact quote's agreement. A quote must also state included work, the four reports, Member inputs, evidence and clarification allowances, field/specialist terms, payment and tax treatment, and written change triggers. Nonproduction test acceptance requires the delivery record. Portable backup/restore includes the agreement bytes and delivery history, with archive-to-record hash verification. A download record proves delivery of bytes, **not** comprehension, legal authority, an executed agreement or payment. Production write paths remain blocked.

A further nonproduction candidate requires a **named Salus reviewer to bind one active Client Executive account to the exact quote** before Member acceptance. The reviewer records an authority basis and a reference to the external evidence reviewed; the record is immutable for that quote, hashed, tenant-scoped, and checked on acceptance and retry. Another signer or altered review fails closed. A reviewer assertion and reference are an auditable decision, not software verification of the underlying charter, delegation, contract or law; qualified commercial/legal review and actual executed terms remain release gates. The review route and acceptance remain locked in production.

The reviewed Member account is also the only Client Executive account allowed to view that fixed quote or download its exact agreement after the review. Before review, the Member view says Salus is confirming the signer, and agreement delivery remains closed. A different Member executive in the same tenant cannot use a shared role alone to receive those terms. Salus report and commercial owners retain their governed internal access. This is draft application behavior, not a claim of live Member access or legal authority.

The candidate does **not** yet bind the Protection Advisor receipt to a verified governed prospect identity. The prospect records are logically isolated by separate tables, sessions and consent rules in the **same application database**; there is currently no Protected Member tenant link. Copying a text receipt ID into SalCAPA would prove neither ownership nor permission to transfer data. The draft quote API now rejects any nonempty `source_receipt_id`, and draft acceptance rejects an older quote carrying one. A Salus-reviewed written scope can still be quoted with an empty source field; that blank must never be presented as an Advisor-linked handoff.

**Required handoff before enabling receipt linkage:** obtain a separate, explicit Part 2 transfer decision from the account owner; authenticate the prospect account and its assessment session; verify submitted status, account ownership, existing Part 2 retention consent, verified account email, exact submission and receipt ID/version, immutable receipt snapshot identity and byte hash. Separately authenticate the tenant-scoped Protected Member decision owner, establish that person's authority over the covered operation, and require a reviewed identity/organization match. Do not infer legal or contracting authority merely from matching email addresses, possession of cookies or a receipt ID. Bind the exact prospect revision and consent record to the same tenant/assessment package identity with an auditable timestamp, access restriction and idempotent retry. Transfer only the approved decision-relevant fields; keep original answers and personal contact data under prospect access controls. Test cross-account, cross-tenant, stale revision, changed boundary, withdrawn consent, deletion, revoked session and duplicate-link cases.

The draft branch now has a **nonproduction-only first handoff step**. An authenticated, email-verified Part 2 account with a submitted profile and saved current receipt may explicitly request a 24-hour claim code under transfer-notice version `SPA-PACKAGE-TRANSFER-0.2.0`. That version has exact plain-language text: the request permits only minimum information for package review, purchases nothing, proves no contracting authority, may be withdrawn while still a draft handoff, and expires after 24 hours. The draft Part 2 page presents the optional notice and checkbox before code creation, lets the person see and withdraw an active handoff on return, hides the feature in production, and excludes the code panel from printing. The server checks account/session ownership, existing retention consent, receipt ID and revision, and saved PDF integrity. A signed-in SalCAPA Client Executive can enter the code and explicitly confirm the selected assessment boundary on a candidate dashboard card. An authenticated Salus Assessment Director or administrator can see a tenant-scoped queue of claimed receipt identifiers without claim codes or contact data, inspect a restricted comparison packet, and download the exact saved receipt PDF with byte-hash verification. The reviewer records separate organization, covered-boundary and decision-role bases against the current assessment version and unchanged prospect content digests. The resulting state is **reviewed for quote preparation only**. It does not independently establish legal contracting authority, incorporate the receipt into signed terms or permit `source_receipt_id` in a quote. The same Part 2 account may withdraw the reviewed handoff without deleting its Advisor profile; prospect deletion also removes it. No contact names, email addresses or answer copies are returned in the claim or review packet. Exact browser display, nonexpert comprehension, a durable contract transfer record and quote binding remain release gates. The production write lock covers all handoff endpoints.

Prospect deletion currently removes the submission and saved receipt bytes; the draft handoff rows are now removed in the same prospect deletion path. Before an approved link or quote is allowed, define the later deletion/retention decision: revoke unused links and quotes when the prospect record is deleted; if a separately authorized signed agreement requires retained contract proof, keep only the minimum governed Member record under its own retention authority and disclose that treatment before transfer. Do not create a foreign key or copy that silently blocks the prospect deletion right or turns a deleted receipt into usable authorization. Review storage, backup, legal hold, claim-code expiration/cleanup and audit behavior together. The draft handoff rows are not yet part of portable tenant backup because they remain unapproved prospect material; restoration and cleanup behavior require specific design before promotion.

The candidate also lacks legal/content approval of the agreement, independent proof of the Client Executive's contracting authority, payment and tax terms, amendments/declines, qualified issued predecessors for Level 2/3, the four exact report issue links, and a plain-language buyer view. The current API fails closed for Level 2/3 quoting and for requoting an authorized assessment. Engineering owns these gates and a reviewed migration/rollback; the product/commercial owner must approve eligibility and non-Access prices; qualified reviewers and Marc control protected issue and promotion. No production state should be inferred from this contract.

The draft now binds each new quote to a digest of the assessment version, purpose, mission, scope, covered operation, exclusions and requested package path. Quote issue and acceptance recheck the current boundary under an assessment lock. A legacy quote without that proof remains historical and cannot be newly accepted. After exact quote acceptance, an authorized Salus reviewer may select a short Level 1 records request from the versioned menu and state why the selected items matter; the same quote/item pair is not duplicated. The signed-in Member may mark a requested item not held, not known or preferred for discussion. The selected request and response survive the local tenant backup/restore test. The draft dashboard shows the selection and Member response views, but contains no file-transfer control. Secure transfer, sector-specific requests, retention and actual browser, accessibility, PostgreSQL and Azure/Wix review remain gates before production use.

The next nonproduction candidate adds four distinct **working Word report** identities under the authorized package: SalINTEL™, SalTHIRA™, SalOPS™ and SalCAPA™. Each new version retains its product identity and records the Protected Member organization, level, band and Access/Standard option in the title; quote and current-scope proof; exact method/template version labels; original storage location; SHA-256; and superseded draft ID. A byte-identical retry is idempotent. The API checks a macro-free DOCX structure and a Clean file scan, restricts upload/list/download to Salus report-owner roles, and requires an explicit assessment assignment for authenticated nonadministrator owners. Draft bytes and lineage are included in local tenant backup/restore validation. These records are **Draft** only. Their version labels are recorded assertions, not approved-template proof or rendered-page QA. No route marks them reviewed, ready, issued, delivered or qualified as a Level 2/3 predecessor. Production candidate routes remain locked. Retention, legal hold, source reconciliation, exact-document review, recipient/issue proof and the predecessor qualification decision remain open release gates.

The nonproduction candidate now records a separate immutable **Charter conformance matrix** for one exact report ID and document SHA-256. A Salus Assessment Director or administrator must mark each required category `Met`, `Pending` or `Not applicable` and explain the evidence, open gate or applicability reason. The saved report bytes, authorized package and scope digest are rechecked before recording; byte-identical matrix retries return the same record, and the matrix plus summary has its own SHA-256. Authenticated report owners require an explicit assessment assignment to view it. Tenant backup/restore validates the report link and matrix digest. `Open` or `Marked` describes only the completeness of that recorded matrix. It is not a qualified reviewer decision, approved template, human issue authorization, recipient delivery or predecessor qualification. The exact page-by-page, accessibility, privacy, source and output-parity checks still have to be performed and supported by evidence outside a self-attested status.

The next nonproduction candidate records a separate **SalCAPA source comparison** against the current exact SalINTEL, SalTHIRA and SalOPS working DOCX identities. The Assessment Director or administrator supplies each source ID, SHA-256, alignment disposition and explanation plus the exact SalCAPA SHA-256 and summary. The API checks all four saved byte hashes, current versions, authorized quote, scope and tenant before an immutable, idempotent comparison record is saved. `Open` means at least one source is unresolved; `Compared` means each source has a recorded disposition. Neither status attests that the comparison is correct or complete, qualifies the analyst, authorizes issue, proves recipient delivery or establishes a Level 2/3 predecessor. Tenant backup/restore validates the source links and comparison digest. Production write paths remain locked.

An internal, nonproduction **package release readiness** view now names the four current report IDs and versions and lists missing or stale draft, stored-byte, Charter-matrix and SalCAPA-comparison proof in plain language. It always reports `Blocked` while independent qualified review, exact rendered/accessibility evidence, controlled issue and recipient proof, and later-level predecessor qualification remain unimplemented. Assigned Salus report owners can read it; a Protected Member cannot. This internal view is a work queue, not an authorization or client deliverable.

The candidate SalCAPA dashboard now shows that internal blocker list to the Assessment Director or administrator for a selected authorized assessment. It never displays the list to a Protected Member and does not offer an issue button. JavaScript syntax has been checked; exact browser, role, accessibility and nonexpert-readback testing remain open before production promotion.

New working reports now receive a retention timestamp under the current application default, with legal-hold and active-disposition fields in their backed-up record. This is a technical preservation floor, not a final records schedule: legal/contractual retention, data-subject treatment, disposal authority, actual object-store lifecycle and backup copies still require governed review before production release.

The nonproduction candidate also accepts an **exact-version report QA archive** for a current working Word report. The draft now also includes a **nonproduction four-report issue packet and named-recipient download path**. The next nonproduction candidate records the named recipient's **explicit receipt and limitations acknowledgment** for one immutable four-report issue.
