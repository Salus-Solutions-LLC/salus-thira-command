# Salus Defender for Storage scanner installation — controlled candidate

**Status:** Source candidate. No Azure scanner, quarantine account, event subscription or clean-result receiver is installed by this document. Production uploads and the Level × Band package routes stay locked until exact live proof and qualified release.

## Existing large-batch intake dependency

This scanner is a security gate for the existing SalCAPA ingestion program, **not a replacement intake system or a second large-batch work order**. [Issue #520](https://github.com/Salus-Solutions-LLC/salus-thira-command/issues/520) already governs nested Microsoft 365/OneDrive batch discovery, a durable per-item ledger, retries, ZIP members, archive verification, large-file handling and Protected Member/engagement isolation. Its v3.202 live worker proved a bounded 20-file pass, not full backlog drain or 10,000-file acceptance. Reuse that ledger and source identity when adding quarantine/scan states; retain the original folder path, version, hash, lineage and retry obligation. Batch files and direct Member uploads must converge on the same exact-object screening rule before extraction or access, while remaining in separately authorized source and destination boundaries. Keep Salus enterprise material separate from unassigned and assigned Protected Member material. The 100 MiB batch-file cap, larger-media transfer, oversize holds and recovery tests remain open under #520 and must be reconciled with the scanner's own limits and charges before media intake is called operational.

## Selected scanner and boundary

Use Microsoft Defender for Storage **on-upload malware scanning** on a dedicated Salus quarantine Blob account. Do not enable it across the whole subscription by default: scope the paid plan to one scanner account. Every accepted media type enters the `quarantine` container as original bytes; no Protected Member, parser, preview, report worker or ordinary evidence download can read from this account. A separate authenticated result handler may copy an exact clean object to the governed evidence account only after matching tenant, blob URI, immutable version/eTag and SHA-256. A copy or transformation is a new object and must retain proof of its original and current bytes. Missing, delayed, `Malicious`, `Not Scanned`, error, timeout, size/cap, password and mismatch results remain quarantined. The receiver and event subscription are **not yet implemented**.

The scanner is a malware gate for documents, photos, scanned handwriting, diagrams, maps, geospatial containers, audio, video, archives and future accepted formats. OCR, transcription, spatial interpretation, file-type policy, rights and content accuracy are separate controls. Microsoft says Defender supports all file types up to 50 GB per blob, but encrypted and complex items can remain unscanned or time out. [Supported content and limitations](https://learn.microsoft.com/en-us/azure/defender-for-cloud/introduction-malware-scanning); [result states](https://learn.microsoft.com/en-us/azure/defender-for-cloud/understand-malware-scan-results).

## Deployment artifact

`infra/azure/defender-storage-scanner.bicep` defines one private, versioned quarantine storage account, a same-region Event Grid custom topic and the resource-level Defender for Storage setting. It uses the stable `2025-06-01` setting API, disables sensitive-data discovery, sends results to Event Grid, avoids blob index tags as an authorization source, declares no file-type exclusions and requires an explicit monthly GB cap. It must be deployed only through the governed Azure identity after the result subscription/handler, cost and isolated storage permissions are reviewed. An unused topic or scanner does not satisfy the Member intake release gate. [Microsoft Bicep resource reference](https://learn.microsoft.com/en-us/azure/templates/microsoft.security/2025-06-01/defenderforstoragesettings); [Event Grid setup](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-storage-configure-malware-scan).

The exact revised monthly cap and current subscription price must be recorded before billable activation; do not silently alter the original foundation budget, its $25 alert threshold or unrelated Azure resources. Microsoft planning material illustrates approximately $10 per protected storage account monthly and $0.15 per GB scanned, plus Blob, Event Grid and processing charges. Those are estimates, not the Salus subscription quote. The monthly scan cap is an availability constraint, **not a guaranteed bill limit**: Azure documents up to 20 GB cap deviation and stops scanning once reached. The application must hold later files rather than mark them clean. [Microsoft planning example](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-product-and-services/security/pdf/From-plan-to-deployment-Implementing-a-cloud-native-application-protection-strategy_Final.pdf); [cost-control behavior](https://learn.microsoft.com/en-us/azure/defender-for-cloud/on-upload-malware-scanning).

## Installation and acceptance sequence

1. Read the current Azure account, location, resource group, storage plan, spend and Microsoft.Security/EventGrid provider registration with the governed workload identity. Confirm only the intended Salus subscription and resource group are targeted.
2. Verify the exact approved cost ceiling, forecast monthly GB of documents and large media, expected account/Blob/Event Grid/handler charges and budget contacts. Set an explicit scanner cap and alerts. Do not interpret an Azure budget as a payment hard stop.
3. Implement and test the event subscription and authenticated result handler. Scope its identity to quarantine read and approved evidence write. Require event origin/topic, exact blob URI, tenant-bound manifest, eTag/version and SHA-256; re-read current bytes before release. Retries must be idempotent and out-of-order events cannot unlock later objects.
4. Build the exact Bicep module; perform Azure `what-if` on that module and inspect resource additions and role assignments. Apply only the reviewed diff through the governed identity, retaining deployment name, parameters, operator, source commit and resulting resource IDs.
5. Upload a clean text file and harmless EICAR test content, then representative PDF, Word, PowerPoint, photo/handwritten image, map, audio, video and archive files. Confirm each original remains inaccessible before result; exact `No threats found` files alone become available. Exercise encrypted, too-large, timeout, scanner outage, cap reached, tampered/replaced object, mismatched tenant, duplicate/stale event and rollback cases. Confirm normal report and evidence access is unchanged for already qualified originals.
6. Reconcile incurred and forecast charges, alert delivery, monitoring, retention/legal hold and support ownership. Record exact image/configuration, logs, hashes and qualified reviewer determination. Only then unlock a named intake path; expand file-type/size acceptance in stages.
