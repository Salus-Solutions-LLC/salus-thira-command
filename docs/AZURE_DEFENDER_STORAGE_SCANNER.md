## Selected scanner and boundary

Use Microsoft Defender for Storage **on-upload malware scanning** on a dedicated Salus quarantine Blob account. Do not enable it across the whole subscription by default: scope the paid plan to one scanner account. Every accepted media type enters the `quarantine` container as original bytes; no Protected Member, parser, preview, report worker or ordinary evidence download can read from this account. The Event Grid topic has a system-assigned identity and may add scan-result messages only to the dedicated `scan-results` queue. The application must read that queue with its own separately scoped identity; it must not accept a caller-supplied event as proof. A result processor may copy an exact clean object to the governed evidence account only after matching tenant, blob URI, immutable version/eTag and SHA-256. A copy or transformation is a new object and must retain proof of its original and current bytes. Missing, delayed, `Malicious`, `Not Scanned`, error, timeout, size/cap, password and mismatch results remain quarantined. The queue processor exists as a tested source candidate but is **not running in Azure**; none of the paid scanner resources is installed.

The scanner is a malware gate for documents, photos, scanned handwriting, diagrams, maps, geospatial containers, audio, video, archives and future accepted formats. OCR, transcription, spatial interpretation, file-type policy, rights and content accuracy are separate controls. Microsoft says Defender supports all file types up to 50 GB per blob, but encrypted and complex items can remain unscanned or time out. [Supported content and limitations](https://learn.microsoft.com/en-us/azure/defender-for-cloud/introduction-malware-scanning); [result states](https://learn.microsoft.com/en-us/azure/defender-for-cloud/understand-malware-scan-results).

`salus_scan_quarantine.py` is a source-only staging/read component for the existing 25 MB path. It uses managed identity and no overwrite, requires a Blob version and ETag, and re-reads the named version with a bounded download and SHA-256 check. The web upload selects the existing runtime identity; only the result worker selects the dedicated quarantine-reader identity. `salus_scan_results.py` qualifies a trusted-queue result against those bytes. The draft intake route has a nonproduction `SALUS_PACKAGE_SCAN_MODE=defender` branch that stages a file and returns `Pending` without adding it to clean evidence; the default inline scanner path remains unchanged. `salus_scan_worker.py` contains a bounded managed-identity queue poll and acknowledgement rule. The draft processor serializes the pending record, checks exact scope and result, re-reads the named blob version, verifies a clean evidence copy and records promotion; adverse outcomes stay held, while a contrary later result suspends the evidence. A 24-hour missing-result reconciliation moves stale originals to a manual hold; a late result cannot automatically release them. These are **source candidates, not an operating scanner**: the scheduled job, identity grants, Event Grid delivery, cost and recovery remain untested in Azure. [Blob client version and download API](https://learn.microsoft.com/en-us/python/api/azure-storage-blob/azure.storage.blob.blobclient); [container version-specific client API](https://learn.microsoft.com/en-us/python/api/azure-storage-blob/azure.storage.blob.containerclient).

The draft `package_intake_pending_scans` table retains tenant, assessment, quote, request, uploader, Blob URI/name/version/ETag, digest, size, hold and retention metadata. Portable backups include this metadata but **never include unscanned original bytes**. Recovery validation reports an external quarantine dependency whenever a record is not promoted; restore changes `Pending` to `Reconcile` so an old result cannot unlock it. Before operational release, prove that the isolated Azure quarantine account retains and can recover each named version under the agreed retention and legal-hold policy, or document a controlled resubmission path. A database backup alone is not complete disaster recovery for held originals.

### Original retention and orphan reconciliation gate

The upload stages bytes before its pending-ledger transaction commits. A failed database commit can therefore leave an original in quarantine with no ledger row. Do not rely on the queue result or a database backup to discover every such object. Before Member use, run an inventory using an identity that may list the quarantine container, compare each exact blob version with the pending ledger, and create a restricted exception record for every unlinked version. Do not grant that list access to the web upload identity. Prove the inventory with a deliberately interrupted staging test and show that an orphan is discovered, isolated, assigned an owner and disposed of only under an approved record. A missing manifest never becomes clean evidence.

`salus_scan_inventory.py` is a read-only source candidate for this comparison. It enumerates versions and hold metadata, rejects duplicate, unversioned, malformed or over-limit inventories, and reports unlinked, missing, size and hold mismatches plus retained bytes. An internal, non-HTTP `inspect_package_quarantine_inventory()` candidate loads the pending ledger and records exact discrepancies in a restricted, server-side exception table. An unlinked original is **not assigned to a Protected Member** from its path. A repeated discrepancy reopens its record; a reviewer must recheck concurrent staging before disposition. The draft deployment now includes a separate daily, five-minute-maximum inventory job, using the reviewed image and restricted reader identity. It logs counts on successful inspection and exits unsuccessfully when discrepancies are observed; an inspection failure logs only the error class and exits unsuccessfully, so a Blob path or token from an exception message is not exposed in routine job output. This is source configuration, **not** a running Azure job or a delivered alert. The job has no approved deletion operation and has not passed an interrupted-staging or legal-hold acceptance test. Prove live execution, failure notification, reviewer response and the retention treatment before Member use.

Retain each recorded original through its applicable retention date and any legal hold. Keep adverse, missing-result and contrary-result originals available for review and recovery. A clean evidence copy does not by itself authorize deletion of the original. A later disposition worker may remove only the exact recorded version after verifying the tenant, assessed retention date, absence of hold, clean-copy status where applicable, and an auditable authorized disposition. Azure Blob versioning and 14-day soft delete in the candidate are recovery aids, **not** a policy that enforces the ledger's retention or legal-hold fields. A ledger flag alone does not place an Azure legal hold on the stored version; prove an appropriate version-level immutability/hold mechanism or a separately controlled preservation process before claims of legal-hold enforcement. Reconcile retained byte totals with the monthly cost forecast and flag growth before the $75 development budget alert. [Azure version-level immutability](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-version-level-worm-policies).

## Deployment artifact

`infra/azure/defender-storage-scanner.bicep` defines one private, versioned quarantine storage account, a same-region Event Grid custom topic, a dedicated result queue, a queue-scoped **Storage Queue Data Message Sender** role for the topic identity, an identity-backed Event Grid subscription and the resource-level Defender for Storage setting. It also defines a custom Blob-write role for the web identity and scoped Blob-read/queue-process roles for the worker identity. The web code uses a unique name and `overwrite=False`; the role itself permits Blob write, so live tests must prove creation, blocked read/list/delete and no overwrite through the web path. The existing subscription Owner identity created only the unassigned preparatory custom role after a reviewed one-resource what-if; the full scanner deployment and container assignment remain pending. The result worker is a scheduled Container Apps Job using an immutable reviewed image digest. Its five-minute schedule starts at most 288 idle executions daily; each execution is bounded to 60 seconds. The separate inventory job runs daily and is bounded to 300 seconds. At the public Container Apps active-rate planning meters already used below, 30 full inventory runs add about $0.07 before other charges; this is a forecast, not a cost cap. Measure queue latency, duration, failed executions, inventory coverage and cost before deployment, then tune the interval or adopt a tested event trigger. A stale-result sweep still needs reliable execution when the queue is empty. The Defender setting depends on the installed jobs and result subscription. It uses the stable `2025-06-01` setting API, disables sensitive-data discovery, sends results to Event Grid, avoids blob index tags as an authorization source, declares no file-type exclusions and requires an explicit monthly GB cap. Deploy only through the governed Azure identity after cost and isolated storage permissions are reviewed. An unused queue, inventory job or scanner does not satisfy the Member intake release gate. [Microsoft Bicep resource reference](https://learn.microsoft.com/en-us/azure/templates/microsoft.security/2025-06-01/defenderforstoragesettings); [Event Grid identity delivery](https://learn.microsoft.com/en-us/azure/event-grid/deliver-events-using-managed-identity); [Event Grid setup](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-storage-configure-malware-scan); [custom roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles); [Put Blob permission](https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob).

Prove the new rules and actual email delivery with controlled failed executions; verify a missing daily run separately, since a failure-only metric alert does not prove the job ran. The result worker entry point also suppresses raw exceptions from its routine job output. It reports only the error class and exits unsuccessfully; held or malformed queue messages remain unacknowledged. This keeps a Blob URL or Member path in an exception message out of the alert's normal log context. A real failed execution and alert must still be inspected for any platform-generated details before release.

The draft worker now checks at most five queue messages per invocation. A malformed or unmatched message remains on hold, but another valid message in that bounded group may still complete and be acknowledged. The run remains failed if any message was held, so the operator must reconcile it. This prevents one bad first message from always stopping the pass; it does **not** supply a poison-message disposition policy or prove the five-item batch fits the 60-second live job limit. Test queue ordering, mixed clean/held results, timeout and alert delivery before activation. [Azure Queue receive semantics](https://learn.microsoft.com/python/api/azure-storage-queue/azure.storage.queue.QueueClient).
