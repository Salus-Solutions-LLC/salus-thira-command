## Media-neutral screening requirement — SAL-D091

Marc requires malware screening for every accepted file/media type, including audio, video, photographs, maps, diagrams, PDFs, Word, PowerPoint, handwritten notes and future formats. The **current draft package-intake form is narrower**: `app.py` accepts PDF, DOCX, XLSX, CSV, TXT, PNG and JPEG, up to 25 MB per file and five files per requested item; production package intake is locked. Its synchronous ClamAV path is not an operating scanner in the production image. Neither a filename allowlist nor a successful text extraction is a malware result. [Microsoft's Defender for Storage documentation](https://learn.microsoft.com/en-us/azure/defender-for-cloud/introduction-malware-scanning) describes all-type blob scanning up to 50 GB but excludes client-side encrypted content and has timeout and other service limits; the [result-state guidance](https://learn.microsoft.com/en-us/azure/defender-for-cloud/understand-malware-scan-results) explicitly distinguishes `No threats found` from `Not scanned` and errors. This supports a media-neutral **candidate** architecture, subject to Salus cost, region and exact-object acceptance.

The existing observation and evidence attachment routes currently accept a scanner result marked `Not Configured` when the optional AV setting is off. That is a concrete SAL-D091 gap across older intake, separate from the locked package path. The migration plan must first establish a working scanner, then require an exact `Clean` result at every accepted file entry and retrieval path, including historic originals that are reprocessed or shared. Do not silently relabel historic `Not Configured` items as clean.

| Accepted material | Malware gate | Separate work after the exact object is clean |
|---|---|---|
| PDF, Word, PowerPoint, spreadsheets and archives | Scan original bytes and inspect scan result for protected, nested or timed-out content; keep such files held. | Safe extraction, OCR where needed, macros/active-content policy, citations and analyst validation. |
| Photos, scans, handwritten notes, maps and diagrams | Scan the original image or geospatial container, including attached or embedded payloads when the engine reports full coverage. | OCR, image/geospatial reading, provenance, location privacy and human interpretation. |
| Audio and video | Quarantine and scan the completed original object before preview or download; use staged large-media transfer and cost/size rules. | Transcription, captions, frame/location metadata review, rights and evidentiary validation. |
| Unknown, uncommon or future types | Do not exempt by extension or MIME. Accept only through a defined intake policy and a scanner path that produces an exact-object result. | Choose qualified specialist handling or a secure alternative when the format cannot be safely processed. |

Implement one ingest state machine across Protection Advisor, Member intake, report-working files and the governed source library: `Quarantined → Scanning → Clean/Rejected/Unscanned/Review`. Only `Clean` can authorize downstream access, and a changed object must reenter quarantine. Bind the result to tenant, container, blob version/eTag and hash; authenticate the result event, verify the current bytes before use and enforce least-privilege access. Route missing, delayed, errored, encrypted, over-size, nested and malicious outcomes to a reasoned Member/reviewer path without exposing content. Measure scan time, per-GB and account charges, storage/event charges, media volumes and backlog against the approved Azure ceiling. Verify clean and harmless test-malware examples for each representative family and rejection cases on the exact image/live environment before extending the accepted file list. A malicious-file test uses controlled harmless test content, not actual malware. Content extraction and analysis remain independently qualified.
